# 設計判断記録 (ADR)

設計判断、採用理由、変更履歴を記録する。新しいエントリは末尾に追加する（古い順）。

## 記録フォーマット

```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-001: project001テンプレートをTRAININGアプリ専用リポジトリへ転用する

- 日付: 2026-09-04
- 状態: 採用

### 背景
- Claude Designで作成したパーソナルトレーニングアプリのデザイン（`Training App プロトタイプ.dc.html`ほか）の実装先として、当初`github.md`に記録されていたNagamaki0311/TRAININGはproject001系のテンプレートのみでUI実装コードを持たなかった。実装先リポジトリを新規に作るか、このリポジトリ自体を転用するかをユーザーに確認した。

### 決定
- 新規リポジトリを作らず、このTRAININGリポジトリ自体をアプリ専用リポジトリへ転用する。README.mdの「新規プロジェクトでの初期化」手順に従い、docs/tasks.md・progress.md・decisions.mdのproject001自身の構築履歴（T-001〜T-026、D-001〜D-025相当）をリセットした。

### 理由
- ユーザーが明示的に選択した。以後はこのリポジトリがアプリ本体として育っていく前提のため、テンプレートの構築履歴を残す意味がない。

### 影響
- 過去のproject001構築履歴（Agent構成・Hook設計等の意思決定）はgit historyには残るが、docs/配下のライブ参照からは削除された。以後のD-XXXはこのアプリの意思決定のみを記録する。

## D-002: プログラム生成ロジックの数値基準を事前リサーチで根拠付ける

- 日付: 2026-09-04
- 状態: 採用

### 背景
- ユーザーから提示された実装プロンプトが、プログラム生成ロジック（種目選定・セット数/回数・進行速度・疲労管理）の実装前に、トレーニング科学のディープリサーチを完了させることを明示的に要求していた。

### 決定
- Web検索でボリュームランドマーク（MEV/MAV/MRV）・週間頻度・自重種目の漸進的過負荷・RPE/ディロード運用に関する学術的知見と実践知見を収集し、`docs/training-science.md`に数値基準として整理した。実装（データモデル・プログラム生成/自動更新/オーバーワーク判定ロジック）はこのファイルの数値を参照する。

### 理由
- 特定の1理論体系（RP方式・5/3/1・PPL等）に固定せず、複数のメタアナリシス・ガイドライン・実践知見を横断して一般的な合意値を採用する方針とした（ユーザー指定の調査軸に準拠）。

### 影響
- 個人差の学習（記録蓄積による閾値調整）は初期値をdocs/training-science.mdの保守的な値からスタートする前提で設計する。将来、実データに基づき数値を見直す場合はこのファイルと合わせてD-XXXを追加すること。

## D-003: F. オンボーディング画面は実装せず、ヒアリング済みプロフィールをシードとして使う

- 日付: 2026-09-04
- 状態: 採用

### 背景
- 実装元の`training_app_prompt_for_design.md`の画面一覧にはF.ログイン/オンボーディング画面が含まれるが、Claude Designでの検討チャット（chats/chat1.md）では「E プログラム自動生成・F オンボーディング」は次のステップとして明示的に提示されたのみで、実際のデザイン（`Training App プロトタイプ.dc.html`）には含まれていなかった。一方、プログラム自動生成にはプロフィール（身長体重・経験・目標・設備・頻度等）が必須である。

### 決定
- プロフィール入力用のオンボーディングUIは実装しない。代わりに、デザイン検討時に収集済みのヒアリング結果（168cm/58kg/1998-03-11生まれ/男性/ほぼ未経験/両方バランス/自重+懸垂バー/週5日×15〜30分/既往歴なし）を`src/state/AppState.tsx`の`SEED_PROFILE`として初回起動時に投入し、そこからプログラムを自動生成する。

### 理由
- 未実装の画面を独自に新規設計することは、デザイン成果物にない要素を推測で作ることになり、Claude Designでのユーザーとの合意事項（12案比較→採用案統合のプロトタイプ）から逸脱する。既知の実データを使う方が確実。

### 影響
- プロフィールを変更する手段が現状ない（設定画面は日次上限時間とデータ削除のみ）。将来プロフィール編集が必要になった場合は別タスクとして追加する。

## D-004: ローカル永続化にAsyncStorage（JSON）を採用し、SQLiteは見送る

- 日付: 2026-09-04
- 状態: 採用

### 背景
- 実装プロンプトはカレンダー機能について「ローカルDB（SQLite等）」を例示していたが、「等」であり必須指定ではない。個人利用・単一ユーザー・データ量も年間数百セッション程度に収まる想定。

### 決定
- `src/storage/db.ts`で`@react-native-async-storage/async-storage`にJSON配列（プロフィール/週間プログラム/セッション記録/設定）を保存するリポジトリ層を実装する。

### 理由
- AGENTS.md判定ラダー（過不足ない最小実装）に照らし、この規模のデータ量・アクセスパターン（月間カレンダー表示・直近数件の履歴参照）ではリレーショナルDBのクエリ機能が不要で、AsyncStorageで十分。リポジトリ層（db.ts）を介しているため、将来SQLiteへ切り替える場合もUI/ロジック層への影響を局所化できる。

### 影響
- 将来的にセッション数が非常に多くなった場合（数千件以上）、全件JSON読み書きのコストが問題になり得る。その場合はdb.tsの実装のみをSQLiteベースへ置き換える。

## D-005: 画面遷移はReact Navigationを使わず、単一の状態遷移（screen state machine）で実装する

- 日付: 2026-09-04
- 状態: 採用

### 背景
- デザイン（`Training App プロトタイプ.dc.html`）自体が、戻るスタックやディープリンクを持たない単一コンポーネントの`screen`状態切り替えとして設計されていた。

### 決定
- `src/state/AppState.tsx`の`Screen`列挙値と`SET_SCREEN`アクションによる単純な画面切り替えのみを実装し、react-navigation等のナビゲーションライブラリは追加しない。

### 理由
- AGENTS.md判定ラダー5〜6（新規パッケージ追加は避ける・1行で書けるか）に照らし、戻るスタック・URL・ネイティブ画面遷移アニメーションが要件にないため、専用ライブラリは過剰。

### 影響
- Androidのハードウェア戻るボタン等、OS標準のナビゲーション挙動とは統合されていない。将来的に画面数が増えて履歴管理が必要になった場合は導入を再検討する。

## D-006: 体感疲労度はセット単位ではなくセッション単位（コンプリート画面）で収集する

- 日付: 2026-09-04
- 状態: 採用

### 背景
- 実装プロンプトはセット単位での体感疲労度記録を要求している。一方デザインの演出方針は「テンポの良さ・待ち時間を発生させない」ことを明示的に重視しており、セット完了のたびに入力を挟むと体験を阻害する。

### 決定
- 体感疲労度はワークアウト完了後のコンプリート画面で1回（5段階）のみ収集し、`SessionRecord.fatigue`として保存する。プログラム自動更新ロジック（`src/engine/progression.ts`）はこのセッション単位の値を直近3セッション分平均して使用する。セッション開始前の体調チェック（睡眠不足・体調不良）はカテゴリ選択画面の2択トグルとして実装し、該当日の目標reps即時軽量化に反映する。

### 理由
- デザインの「テンポを阻害しない」方針を優先しつつ、工程2で要求された疲労・体調補正ロジックの入力を確保するための折衷案。

### 影響
- セット単位の疲労推移は記録されない（`SetRecord`に疲労度フィールドは持たせていない）。将来より粒度の細かい記録が必要になった場合はUI設計から見直す。

## D-007: clip-pathによる斜めカット表現は、角丸・単純形状へ簡略化する

- 日付: 2026-09-04
- 状態: 採用

### 背景
- デザイン（.dc.html、CSS/HTML）はボタンやカードの角を`clip-path: polygon(...)`で斜めにカットする表現を多用している。React NativeのStyleSheetにはCSSのclip-path相当の機能がない。

### 決定
- 斜めカット表現は角丸（borderRadius）や単純な矩形へ簡略化する。休息タイマーの円環（conic-gradient相当）のみ、視覚的に中心的な要素のため`react-native-svg`を追加し`Circle`のstrokeDasharray/strokeDashoffsetで再現する（`src/screens/components/RestRing.tsx`）。

### 理由
- AGENTS.md判定ラダーに従い、標準コンポーネントの組み合わせでは代替できない視覚要素（休息タイマーの円環進捗）にのみ新規依存を追加し、それ以外はネイティブのborderRadius等で表現可能な形に簡略化した。

### 影響
- ボタン・カードの角の視覚的な「鋭さ」はオリジナルデザインよりやや弱まる。将来react-native-svgをボタン背景にも使えば再現度を上げられるが、実装コストとのトレードオフとして見送った。

## D-008: 敵対的レビューで発見された最終セット処理の競合状態を修正

- 日付: 2026-09-04
- 状態: 採用

### 背景
- REVIEW.md準拠の敵対的レビュー（general-purposeエージェントへ委任）で、`completeSet`がセッション最後のセットを完了した際、`phase`が`'work'`のまま`finishSession`実行（900ms後）まで「セット完了」ボタンが操作可能な状態で残り、(1)連打で`SetRecord`とセッション保存が重複する、(2)その間に「中断」しても保留中の`finishSession`がキャンセルされず記録済みセッションが強制保存されてComplete画面へ引き戻される、という2件のHigh指摘（CONFIRMED）を受けた。あわせて`fullHitHistoryFor`（progression.ts）・「直近の履歴」（HomeScreen.tsx）の日付ソートcomparatorが同値で0を返さず、同日複数セッション時に順序が不定になる指摘（CONFIRMED、2箇所）、および`finishSession`のAsyncStorage書き込みにエラーハンドリングが無くワークアウト実行画面に固定され得る指摘（PLAUSIBLE）を受けた。

### 決定
- `ActiveSession`に`finishing`フラグを追加し、最終セット完了時に`true`にする。`completeSet`は`finishing`中は再入を無視し、UI側（WorkoutScreen）も完了ボタンを無効化する。
- `completeSet`が仕掛けるタイマー（フラッシュ解除/finishSession実行）のIDを`AppStateProvider`の`useRef`で保持し、`quit`実行時に明示的に`clearTimeout`する。
- 日付文字列の降順ソートcomparatorを同値で0を返す実装へ修正（2箇所）。CLAUDE.mdに⚠️絶対ルールとして恒久化（REVIEW.md「同一種別の指摘が繰り返された場合の恒久化」に基づく）。
- `finishSession`のAsyncStorage書き込み（appendSession/setProgram/setSettings）をtry/catchで包み、失敗してもユーザーが実行画面に固定されないようdispatchは必ず実行する。

### 理由
- いずれも実際に到達可能な操作（連打・素早い中断操作）で発生し、記録の重複・意図しない保存・画面固定という形でデータ整合性とUXの両方を損なうため、必須修正（REVIEW.mdの分類でLow/Nit降格の対象外）と判断した。

### 影響
- ストレージ書き込み失敗時、当該セッションの記録・プログラム自動更新・ストリーク加算が保存されない場合があるが、エラーはconsole.errorに記録されるのみでユーザー通知は行っていない（トースト等の通知UIは本スコープでは未実装）。将来的にリトライ/通知が必要になった場合は別タスクとする。
